# Pruebas del 2026-11-16

Registro de la primera versión de este repositorio: la capa antialucinación,
separada del agente de criptomonedas para que sirva en cualquier rubro.

## De dónde viene

La capa se escribió y se probó dentro del agente de criptomonedas de
CryptoCapi, un repositorio privado, y sale de ahí tal como estaba en su commit
`8bc7b5b` (su release v1.4.0): el paquete `antihallucination/`, sus tests
(sin el prefijo `test_ah_`), las respuestas reales de un modelo y el ejemplo
de ventas. El registro de pruebas anterior, con el detalle de cada corrida,
quedó en ese repositorio.

Lo nuevo de este repositorio:

- Se instala con `pip`: `pyproject.toml`, el comando `antihallucination` y el
  marcador `py.typed` para quien lo use con un verificador de tipos. Las
  comprobaciones solo usan la biblioteca estándar; httpx viene para los modelos
  compatibles con OpenAI y el SDK de Anthropic es un extra (`[claude]`).
- Dos ejemplos de otros rubros, en inglés: métricas mensuales de un SaaS y un
  resumen de tickets de soporte que cita cada ticket. Un test fija lo que
  muestra cada ejemplo.
- Un README escrito para cualquier rubro, sin nada de criptomonedas.
- Un CI con tres trabajos: los tests en Python 3.11, 3.13 y 3.14; solo las
  dependencias que trae `pip install`; y el paquete instalado, usado desde
  fuera del repositorio.

## El servidor MCP

Para que la capa sirva a quien no programa: un asistente compatible con MCP
(Claude Desktop, Claude Code u otros) redacta, y el servidor escribe las cifras
y comprueba cada oración. No llama a ningún modelo ni a la red.

- Se escribió sobre el SDK oficial `mcp` 2.3.0, revisado instalado: en la 2.x
  `FastMCP` pasó a llamarse `MCPServer`, y un error común llega al cliente sin
  su motivo, por eso los errores de datos salen como `ToolError`.
- Cuatro herramientas de solo lectura: `prepare_report` (marcadores y reglas,
  sin ninguna cifra), `compose_report`, `verify_text` y `check_receipt`.
- En un chat el asistente ya vio las cifras, así que el encargo le prohíbe
  teclearlas en lugar de decirle que no se las muestran.

## Los cambios los calcula la capa

La segunda sesión de Claude Code mostró el hueco: el modelo calculó el 16,1 %
y lo pasó como un dato más. Ahora el cambio entre dos datos lo calcula la capa:

- En Python, `percent_change()` y `difference()` arman el dato a partir de
  otros dos, como `classify()` arma un veredicto. En los datos del comando y
  del servidor MCP es un dato con `compute` (`percent_change` o `difference`),
  `from` y `to`, sin `value`.
- El valor se guarda exacto y se escribe con la precisión pedida (un decimal
  por defecto en un porcentaje). Toma la unidad de sus datos. La diferencia
  entre dos porcentajes va en puntos (`pp`), y la variación porcentual entre
  ellos se rechaza: «bajó 8 %» y «bajó 0,2 puntos» salen de los mismos 2,5 % y
  2,3 %. También se rechazan la variación porcentual desde cero y la que
  compara unidades distintas.
- Un dato que dice ser calculado y trae otro valor se rechaza antes de
  cualquier comprobación.
- El recibo (receta `antihallucination/0.3`) dice en cada dato si vino dado o
  si se calculó, y a partir de cuáles. Al repetir la decisión se vuelve a
  calcular: un valor editado da `different` aunque se haya rehecho el digest.
  Los recibos de la receta 0.2 ya no se leen con esta versión.
- Las instrucciones del servidor le piden al asistente que no calcule ninguna
  cifra y que pida los cambios con `compute`.

|---|---|
| Tests, mypy y ruff | 251 tests pasan en Python 3.14 y en 3.11 (en Docker); mypy y ruff sin errores |
| Una sesión nueva de Claude Code (`claude -p`, versión 2.1.325, Opus 5.5) con el servidor de este código, instalado en un entorno aparte | Pedido: «un informe corto de octubre … que diga cuánto subieron las ventas», con 1.240 unidades en septiembre y 1.440 en octubre. Sin que nadie le nombrara `compute`, le pidió al servidor la diferencia y la variación porcentual. El texto dice que las ventas subieron 200 unidades, un 16,1 %, y el recibo marca las dos cifras como calculadas a partir de las ventas de septiembre y octubre. `check_receipt`: `verified` y `reproduced` |

En esa sesión el modelo mandó primero una `unit` en la diferencia, el
servidor la rechazó y el modelo la sacó. Después de la prueba se aceptó repetir
la unidad que el dato toma de todas formas; cambiarla se sigue rechazando.

La revisión antes del commit encontró que la variación porcentual dependía de
la precisión decimal de quien llama: `abs()` redondea con ella, y con 4 dígitos
el cambio de 123.456 a 234.567 daba 89,97 % en lugar de 90,0005 %. Un replay
podía dar distinto. Ahora el cálculo no usa ese contexto, y un test lo fija.
También `write()` rechaza un dato calculado inconsistente antes de llamar al
modelo, no después.

Lo que no cambia: los datos de origen los sigue pasando el modelo. La capa
garantiza la cuenta, no que 1.240 y 1.440 sean las ventas reales.

## El servicio HTTP y la imagen Docker

Para quien prefiere llamar a un servicio en lugar de sumar Python a su agente.
`antihallucination serve` sirve en un solo proceso los mismos cuatro chequeos
que el servidor MCP:

- Una API REST (`/v1/prepare`, `/v1/compose`, `/v1/verify` y `/v1/receipt`)
  que recibe el mismo JSON de datos que el comando y devuelve lo mismo que las
  herramientas MCP.
- MCP por HTTP en `/mcp`, sin estado y con respuestas JSON: cualquier
  instancia detrás de un balanceador contesta cualquier pedido.
- No llama a ningún modelo, así que quien llegue al servicio no puede gastar
  tokens de un proveedor.
- Con `ANTIHALLUCINATION_TOKEN`, todo menos `/health` exige
  `Authorization: Bearer`. Sin token solo arranca en 127.0.0.1; la imagen, que
  escucha en todas las interfaces, no arranca sin él.
- Rechaza pedidos de más de 256 KB. El tiempo de revisión crece en línea con
  el texto: en la máquina de pruebas, 64 KB tardan 0,19 s; 256 KB, 0,7 s, y
  1 MB, 2,8 s.

| Comprobación | Resultado |
|---|---|
| 24 tests nuevos: REST con el cliente de pruebas de Starlette, MCP por HTTP con el cliente del SDK contra un servidor real, y las negativas de `serve` | Pasan; con el resto, 275 tests |
| La imagen, construida en la máquina de pruebas | 239 MB; corre como un usuario sin privilegios y el healthcheck da `healthy` |

## Textos largos que tardaban minutos

Una revisión de seguridad del servicio encontró que una oración larga sin
puntuación tardaba en revisarse el cuadrado de su largo: `"revenue grew "`
repetido hasta 31 KB tardó 27 s. Al medir otras formas de texto apareció que no
era un caso suelto. Varias partes de la revisión volvían a leer la oración
entera por cada palabra, y una por cada palabra y cada cifra. Los tiempos de
la sección anterior (256 KB en 0,7 s) valen para un texto común, no para
cualquier texto. Afecta a todo lo publicado: la librería, el comando y el
servidor MCP de la 0.2.1.

- Los límites de la cláusula y las tres palabras antes de un verbo de
  movimiento se buscaban desde el principio de la oración en cada palabra.
- Los sujetos se buscaban hasta tres veces por palabra de movimiento, y con
  muchos datos cada patrón se volvía a compilar.
- Cada cifra sin su signo menos revisaba toda su cláusula, y cada veredicto
  se comparaba con cada cifra.
- Al leer las cifras, cada una se comparaba con todas las anteriores.
- Al cortar oraciones, cada punto que no corta (el de una inicial o de «etc.»)
  volvía a leer la línea desde el principio. Y una tira de puntos sin espacio
  después hacía retroceder a la expresión regular en cada punto.

Ahora cada oración se lee una vez: las cláusulas se ubican una vez y se
consultan con búsqueda binaria, la negación lee hacia atrás solo hasta la
tercera palabra, los sujetos se buscan una vez por cláusula y el resto una vez
por pedido. Las decisiones no cambian.

| Texto | Antes | Ahora |
|---|---|---|
| `"revenue grew "` repetido, una sola oración | 22 s con 32 KB | 0,7 s con 256 KB |
| `"no fell {drop:abs} "` repetido, en `compose` (crecía con el cubo del largo) | 6,7 s con 4 KB | 1,2 s con 256 KB |
| `"a. "` repetido: puntos que no cortan la oración | 13 s con 64 KB | 0,9 s con 256 KB |
| `"1 tres "` repetido: cifras y números en palabras | 13 s con 64 KB | 2,5 s con 256 KB |
| 40.000 puntos seguidos, sin espacio después | 30 s | 0,5 ms |

## Texto y datos grandes a la vez

Con el largo del texto resuelto, quedaba lo que crece con el texto por los
datos: cada cifra se comparaba con cada fact, cada oración con cada fuente, y
una cadena de facts calculados se leía una vez por eslabón. Y algo peor: con
miles de facts del mismo valor, cada cifra vale por todos, cada decisión los
lista y el recibo explota. Un pedido de 16 KB daba un recibo de 135 MB.

Son cuatro cambios, para la 0.3.0:

- Índices que no cambian ninguna decisión. Cada cifra mira solo los facts a los
  que puede redondear. Cada sujeto, nombre o etiqueta citada se busca solo en
  un texto que tenga todas sus palabras, y un sujeto se indexa por su palabra
  más rara. Cada identificador se busca entre los tokens de las fuentes, y lo
  que dicen las fuentes se junta una vez por pedido. Los facts calculados se
  resuelven por rondas.
- Un tope en la librería: si el texto coincide con los datos más de 200.000
  veces (facts que una cifra puede representar, más etiquetas que una oración
  puede citar), se rechaza con `TooManyMatches`. Los ejemplos del repositorio
  llevados a 256 KB gastan entre 1.300 y 6.500.
- Una cifra que representa varios facts negativos sin decir que cayeron da un
  solo `sign_dropped`, que nombra el primero y cuenta los demás. Antes daba uno
  por fact. Cambia el recibo en ese caso; la receta 0.3 todavía no se publicó.
- En el servicio, cada pedido corre en un proceso aparte, con tiempo (10 s) y
  memoria (1024 MB, en Linux y macOS) máximos. Pasado cualquiera de los dos, la
  respuesta es 413 y el servicio sigue. El tiempo lo cuenta el propio proceso,
  así que no incluye su arranque, y el servicio mata al que no se detenga. El
  primer pedido de un servicio recién arrancado tarda cerca de 1 s más.

| Texto y datos, mitad y mitad | Antes | Ahora |
|---|---|---|
| Cada cifra contra cada fact, 64 KB | 15 s | 0,23 s |
| Cifras contra 2.000 fuentes chicas, 128 KB | 20 s | 0,58 s |
| Nombres contra una fuente larga, 128 KB | 5,1 s | 0,17 s |
| Sujetos de muchos facts contra muchas oraciones, 128 KB | 6,7 s | 0,36 s |
| Respaldos contra muchas oraciones que fallan, 128 KB | 11,7 s | 0,16 s |
| Una cadena de facts calculados, al revés, 128 KB | 17 s | 0,02 s |
| Mil etiquetas con el mismo texto, citadas, 64 KB | 58 s | rechazado en 0,2 s |

Con 256 KB, toda forma medida tarda como mucho 1,1 s o se rechaza en menos de

## Números con un exponente enorme

El servicio lee los números del JSON como decimales exactos, y el recibo
escribe cada valor completo, sin exponente. Un pedido de 64 bytes con un fact
que valía `1e-10000000` recibía una respuesta de 10 MB. Con `0e-10000000`
pasaba lo mismo, porque el cero guarda sus decimales. Con `1e10000000` la
respuesta era 500. Antes del proceso aparte de la sección anterior,
`1e1000000000` llevaba el contenedor a unos 3,5 GB y lo tiraba. Por MCP no
pasa, porque ahí el número llega como float.

Buscando el arreglo apareció otro problema, que también está en la 0.2.x. Las
cuentas con un valor se hacían en el contexto decimal de Python, que redondea
a 28 dígitos. Un valor más largo que eso fallaba al redondearse para
escribirlo (500 en el servicio). Y al revisar un texto, una cifra que difería
del fact después del dígito 28 pasaba como si fuera la del fact.

Son dos cambios, para la 0.3.0:

- Un valor tiene como máximo 40 dígitos escrito entero: `1e39` y `1e-39`
  entran, `1e40` no. Uno más largo da `ValueError` en la librería y 400 en el
  servicio, con un mensaje corto. Lo mismo un recibo editado para traerlo. Es
  una sola regla, en vez de un rango de magnitudes, para que cubra también el
  cero.
- Escribir y comparar un valor ya no depende del contexto decimal de quien
  llama. Se redondea en un contexto fijo de 80 dígitos, y la cifra leída del
  texto se compara con el fact sin redondear ninguna de las dos.

|---|---|
| Los tres pedidos de 64 bytes | 400 con un mensaje de 99 bytes. Antes, 10 MB, 10 MB y 500 |
| Tests nuevos | 17: valores de más de 40 dígitos, valores de hasta 40 escritos enteros en el recibo, cifras de 40 dígitos con 12 decimales en un contexto de 4 dígitos, una cifra que difiere después del dígito 28, el recibo editado y los tres pedidos. ## Vulnerabilidades conocidas en la imagen

Trivy 0.70.0 sobre la imagen de `main` encontró 8 vulnerabilidades en paquetes
de Python (5 altas) y 220 en Debian 13.7 (48 altas). Las de Python estaban
todas dentro de pip, en los paquetes que trae adentro: urllib3 2.7.0, msgpack
1.1.2 y el `pkg_resources` de setuptools 70.3.0. El servicio no usa pip. De las
de Debian, solo 2 tenían arreglo publicado, las dos en zlib. Las demás están
en paquetes esenciales de la base (libc, util-linux, openssl, perl-base,
ncurses) y Debian todavía no las arregló.

El Dockerfile ahora instala los arreglos de Debian publicados después de la
imagen base (`apt-get upgrade`) y desinstala pip al terminar de instalar el
paquete. La imagen se construye de nuevo en cada release, así que cada una trae
los arreglos publicados hasta ese día.

| Comprobación | Resultado |
|---|---|
| `trivy image`, antes y después | Python: de 8 a 0. Debian: de 220 a 218 (47 altas), ninguna con arreglo publicado |
| `trivy config Dockerfile` | Sin hallazgos |
| La imagen nueva, como la llama el CI | Sin token no arranca (sale con 2); `/health` responde; sin token en el pedido, 401; el ejemplo de ventas, 200; `1e-10000000`, 400; el healthcheck da `healthy`; corre como el usuario `service`, y pip ya no está |

Lo que queda en Debian solo baja cambiando de imagen base, por una más chica
que no traiga esos paquetes.

## El servicio, endurecido

Lo último de la revisión de seguridad: nada de esto se podía aprovechar con el
servicio como estaba, pero cada punto dejaba una puerta que no hacía falta.

- **TLS y el token.** El servicio habla HTTP plano, y el README no lo decía.
  Ahora dice que el token y los informes viajan en claro sin TLS, que va
  detrás de un proxy que lo termine o en una red privada, y genera el token con
  `openssl rand -hex 32`.
- **Pedidos desde una página web.** Sin token, en `127.0.0.1`, las rutas REST
  aceptaban un POST de cualquier origen y con cualquier `Host`. Una página
  podía hacer que el navegador le mandara texto plano, o apuntar un nombre
  suyo a 127.0.0.1 (DNS rebinding). `/mcp` ya lo rechazaba, por el SDK de MCP.
  Ahora las rutas REST hacen lo mismo: un POST tiene que decir
  `Content-Type: application/json` (si no, 415), y en un servicio local el
  `Host` y el `Origin` tienen que ser locales (si no, 421 y 403).
- **Acciones fijadas.** En `publish.yml`, las acciones de Docker corren con
  permiso para publicar la imagen, y la de PyPI con el de publicar el paquete.
  Iban por tag, que su dueño puede mover. Ahora van por commit, con la versión
  al lado. Las de GitHub (`actions/*`) siguen por tag.
- **500 en lugar de 400.** Un JSON anidado más allá de lo que Python puede leer
  (50.000 corchetes) daba 500. Ahora da 400, «the body is nested too deeply».
  El otro 500 de este punto, al redondear una cifra enorme, ya no ocurre desde
  el límite de 40 dígitos.

| Comprobación | Resultado |
|---|---|
| `antihallucination serve` en 127.0.0.1, sin token, con curl | REST y `/mcp`: 200 con lo local; 421 con `Host: evil.example`; 403 con `Origin: http://evil.example`. REST con `text/plain`, 415 |
| La imagen (escucha en 0.0.0.0, con token) | Sin token no arranca; sin token en el pedido, 401; ventas, 200; `text/plain`, 415; un `Host` de la empresa, 200; 50.000 corchetes, 400; el healthcheck da `healthy` |
| Tests nuevos | 18: los `Host` y `Origin` locales y ajenos, un servicio que no es local, `/mcp` con un `Host` ajeno y con 50.000 corchetes, `text/plain`, el JSON anidado en dos rutas y la pila que se acaba. Con el código anterior fallan 10; los otros 8 fijan lo que ya andaba |
| Tests, mypy y ruff | 345 tests pasan en Python 3.14 en Windows y uno se saltea (el del tope de memoria). En 3.11, 3.13 y 3.14 sobre Linux (en Docker, con git) pasan los 346. mypy y ruff sin errores |

## La evaluación: el piloto

Hasta acá se probó que las reglas hacen lo que dicen; falta medir cuánto
atrapan. La evaluación vive en `benchmark/` y su plan está en
`benchmark/README.md`: modelos que escriben informes a partir de datos, sin la
capa; personas que etiquetan cada oración con los datos a la vista, sin saber
qué modelo la escribió ni qué decidió la capa; y `verify()` medido contra esas
etiquetas.

Lo que quedó hecho el 2026-11-18:

- **La guía de etiquetado** (`benchmark/GUIA.md`): tres veredictos (correcta,
  neutral, error) y trece tipos de error en dos grupos, errores de hecho y
  agregados sin respaldo. Incluye errores que la capa no busca, como un hecho
  inventado o una recomendación, para que la taxonomía no copie las reglas.
- **Los conjuntos de datos**: 120 sintéticos, con semilla fija, en cinco
  rubros y dos idiomas, parejos. 20 del piloto y 100 de la fase 1 (30 de
  desarrollo, 70 de prueba). Todo es inventado.
- **Los informes del piloto**: 40, de `openai/gpt-oss-120b` y
  `qwen/qwen3.8-27b` en Groq, la mitad con un prompt que pide usar solo los
  datos. Groq ya no servía modelos Llama de texto. Son 273 oraciones; 11
  informes (78 oraciones) quedan para la segunda persona.
- **La página de etiquetado**, en claude.ai: cada persona guarda en su propio
  espacio, y las reglas de la página le esconden a cada una las etiquetas de
  la otra.
- **`benchmark/evaluate.py`**: recall, precisión y falsas alarmas de la capa,
  de sus controles de cifras solos y de una regex ingenua, con intervalos del
  95 % por informe, y el acuerdo entre las dos personas.

| Comprobación | Resultado |
|---|---|
| Los conjuntos contra el script | `make_datasets --check` coincide; un test lo corre en cada versión de Python del CI |
| Las oraciones de la página contra las de `verify()` | Iguales en los 40 informes del piloto |
| Las métricas sobre un caso etiquetado a mano | Dan lo esperado, acuerdo entre dos personas incluido |
| La página, publicada | Las lecturas como dueño y como Editor vuelven vacías, como debe ser antes de etiquetar. Una escritura solo la puede hacer la página: se verifica con las primeras etiquetas |
| Tests, mypy y ruff | 355 tests pasan en Python 3.14 y uno se saltea; mypy y ruff sin errores |

La fase 1 empezó y se frenó. La clave de Groq que se usó es de una cuenta
con un servicio en producción, y en Groq los límites son por cuenta, no por
clave. Entre las 11:21 y las 11:37 (hora de Argentina) se pidieron 88
informes, y Groq frenó más de 40 veces por límite. Quedaron 48 de los 300
informes de la fase 1. La
generación sigue con una cuenta de Groq propia de la evaluación, y retoma
donde quedó.

Algo que ya se vio sin etiquetar: `gpt-oss-120b` separa los miles y el signo
de porcentaje con un espacio angosto especial (`83 662`, `4,0 %`). Los tests
de la capa no tienen ese formato; la evaluación va a decir cómo lo lee.

## Lo que encontró el piloto

Las 273 oraciones del piloto las etiquetó primero Codex, un asistente de IA,
en 12 minutos y sobre el paquete local. Sus etiquetas están en
`benchmark/labels/pilot-codex.json`, con sus notas al lado. Una IA no puede
ser la verdad de la evaluación, así que los números de esta sección son
provisorios. Esas etiquetas van a servir como la alternativa del «modelo como
juez». Lo que sí vale sin depender de quién etiquetó es lo que mostraron:
oraciones correctas que la capa cortaba por cómo estaba escrita una cifra o
una palabra.

- **La cifra como la escribe la capa.** La capa calculaba una variación de
  0,76 %, la escribía `0,8 %`, el modelo la copiaba y la capa la rechazaba,
  porque una cifra de una sola cifra significativa tenía que ser exacta. Ahora,
  escrita con la precisión con que la capa escribe el dato, se compara contra
  el dato redondeado así. `3 %` por 2,9 % se sigue rechazando: la capa escribe
  `2,9 %`.
- **Miles con espacios tipográficos.** `gpt-oss` escribe `83 662` con un
  espacio angosto. Ahora el espacio angosto, el no separable y el fino agrupan
  miles; el espacio común no, porque separa dos cifras.
- **Versiones.** `3.2.4` no tenía ninguna lectura, así que nada podía
  respaldarlo, ni siquiera la nota que lo traía. Ahora se revisa como un
  nombre: tiene que estar escrito en los datos o en una fuente.
- **Números en lo que mide un dato.** El `24` de «volumen operado en 24 horas»
  queda respaldado cuando va con la misma palabra: «24 horas», «24-hour». El
  mismo número con otra palabra, o como porcentaje, no.
- **Palabras.** Faltaban participios y gerundios que dicen que algo bajó o
  subió («ha retrocedido», «ha caído», «reduciéndose»), y la capa no reconocía
  un nombre conocido en posesivo («Marlow Supply's»). Los participios que
  suelen ser adjetivos, como «reducido», siguen afuera.

Un arreglo abrió un agujero que la comparación al azar encontró antes del
commit: en `3 2026`, con un espacio no separable, los dos números dejaban de
revisarse. Un grupo de miles con espacio ya no puede ir seguido de otro
dígito, y hay un test para eso.

| Contra las etiquetas de Codex | Antes | Después |
|---|---|---|
| Errores que atrapa | 46 % | 37 % |
| Precisión | 72 % | 88 % |
| Oraciones correctas cortadas de más | 34 % | 9,5 % |
| De esas, por el control de cifras | 22 % | 0 % |

Los errores que atrapa bajaron porque varias oraciones con errores de otro
tipo caían solo porque la capa leía mal sus números: acertaba por la razón
equivocada.

| Comprobación | Resultado |
|---|---|
| Tests nuevos | 20. Con el código anterior fallan 16; los otros 4 comprueban que no se abrieron agujeros: el espacio común entre dos cifras, `3 2026` como dos cifras, una versión que nadie escribió y «reducido» como adjetivo. Dentro de los que fallan, otras afirmaciones cuidan que `3 %` por 2,9 % y el número de una métrica con otra palabra se sigan marcando |
| Contra `HEAD`, con 4.000 documentos al azar | Cambian 50, y los 50 se explican: versiones que ahora se revisan como nombres y un grupo de miles con espacio |
| Tests, mypy y ruff | 375 tests pasan en Python 3.14 y uno se saltea; mypy y ruff sin errores |

Las 9 oraciones correctas que la capa todavía corta son de tres clases: la
dirección atribuida a otra métrica (como «pese a **esta** reducción», que se
refiere a la oración anterior), oraciones sin cifras que resumen una nota sin
citarla, y causas o fechas futuras que la nota sí dice pero la oración no
cita. Además, de los 177 errores que marcó Codex, 143 son «juicio sin
respaldo», casi todos por palabras de grado («slight», «estable»,
«significativa»). La guía se revisa con eso.
